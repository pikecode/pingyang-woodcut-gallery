## 数据口径

正式数据以文档为主。每个正式文档中的每条记录都先作为独立作品保存，不因为题名相同而去重或合并。

原因是这些文档中存在同题作品，但同题不等于重复。它们可能是：

- 不同版本；
- 同题异图；
- 同题但画面内容不同；
- 同题但描述、分类、年代、尺寸不同；
- 同一题材在不同批次中的独立登记。

因此 staging 数据采用“来源文档 + 源内编号 + 全局正式编号”的方式保存，并额外记录同题关系：

```text
officialNo: 全局正式草稿序号，1–221
slug: official-{sourceCode}-{sourceNo}
source.code: 来源文档编码
source.recordIndex: 源文档内顺序
source.catalogNo: 主 .doc 中的原始编号；登记表为空
sameTitleGroup: 同题作品组；无同题作品时为空
sameTitleCount: 同题作品数量
```

示例：

```text
official-main102-001  牛郎织女
official-main102-087  赵云救阿斗
official-reg42-001    赵云救阿斗
```

这说明 `赵云救阿斗` 在主文档和登记表中都出现过。它们作为两条正式作品保存，同时通过 `sameTitleGroup` 建立同题关系。

## 正式数据结构

正式数据以程序展示为主，顶层保留 5 个最重要字段：

| 字段 | 含义 | 用途 |
|---|---|---|
| `title` | 标题 / 作品名称 | 列表、详情页标题 |
| `category` | 类别 | 分类页、筛选、标签展示 |
| `content` | 内容说明 | 详情页正文、导览文案基础 |
| `images` | 图片 | 列表图、详情图、后续对象存储迁移 |
| `sourceRef` | 文字来源定位 | 人工核对标题、类别、内容是否正确 |
| `imageSourceRef` | 图片来源定位 | 人工核对图片来自哪个高清文档记录 |

示例：

```json
{
  "title": "牛郎织女",
  "category": "拂尘纸",
  "content": "画面上方点缀星辰，下方云间喜鹊搭成鹊桥……",
  "images": [
    {
      "role": "primary",
      "path": "assets/official-originals/main102/001-01-primary.jpg",
      "width": 663,
      "height": 319
    }
  ],
  "sourceRef": {
    "document": "平阳木版年画（102幅）.doc",
    "documentCode": "main102",
    "recordIndex": 1,
    "catalogNo": 1,
    "label": "平阳木版年画（102幅）.doc 第 1 条"
  },
  "imageSourceRef": {
    "document": "平阳木版年画（102幅）.doc",
    "documentCode": "main102",
    "recordIndex": 1,
    "catalogNo": 1,
    "title": "牛郎织女",
    "label": "平阳木版年画（102幅）.doc 第 1 条"
  }
}
```

说明：

- `category` 已经是正式展示分类，主文档以块内字段表里的 `类别` 为准。
- `content` 是正式内容说明，不包含标题下方的类别摘要和馆藏摘要。
- `sourceRef.label` 是文字内容人工 review 时最直接的定位字段。
- `sourceRef.recordIndex` 表示在源文档中解析出的第几条。
- `sourceRef.catalogNo` 只在主文档有值；登记表没有原始编号时为 `null`。
- `imageSourceRef` 表示图片来自哪个高清文档记录。多数情况下和 `sourceRef` 同编号，但在新旧文档标题修订或旧文档多一条记录时，二者可能不完全一致。

其他字段作为辅助信息保留：

| 字段 | 说明 |
|---|---|
| `officialNo` | staging 全局序号 |
| `slug` | 程序内部稳定 ID |
| `theme` | 兼容旧 Desktop 数据结构的分类对象 |
| `description` | 兼容旧 Desktop 数据结构的说明字段，内容等同于 `content` |
| `sourceFields` | 原始摘要字段、原始类别、原始尺寸、原始馆藏 |
| `sameTitleGroup` | 同题作品关系 |
| `issues` | 当前记录需要人工确认的问题 |

## 图片策略

项目之前的原则是“图片保留原始体积，后续可能存储到其他地方”。正式数据继续按这个原则处理。

建议分两层：

1. 原始图片层

   - `.docx` 图片从高清来源文档的 `word/media` 原样抽取；
   - 不压缩、不改尺寸；
   - 记录 sha256、bytes、格式、宽高；
   - 后续可以迁移到对象存储。
   - 主 `.doc` 图片从高清来源文档的 Word 97 OLE `Data` 图片流原样抽取。

2. Desktop 展示层

   - 从原图生成 WebP 展示图；
   - 放到 `desktop/public/images`；
   - 用于列表、详情、开屏动画；
   - 这是可再生成资产，不作为正式原始资产。

主 `.doc` 的文字来自修订版文档，图片来自旧高清文档。旧高清 `平阳木版年画（102幅）.doc` 文件约 465MB，抽出的主文档图片为高清图；脚本只原样抽取，不压缩。

## Desktop 替换方案

正式替换不建议一次性直接覆盖。推荐分 4 步：

### 第一步：确认 staging 数据

确认：

- 221 条是否都要进入 Desktop；
- 同题作品是否全部保留；
- `未分类`、空尺寸是否接受先展示；
- `image_source_title_differs` 的 15 条是否确认可以按当前映射使用。

### 第二步：抽取正式原图

执行正式原图抽取：

```sh
python3 -m pip install -r requirements.txt
python3 scripts/import_official_gallery_docs.py \\
  --extract-images \\
  --image-source-dir '/Users/ompeak/Desktop/aaa/平阳木版年画'
```

其中 `olefile` 用于解析 `平阳木版年画（102幅）.doc` 的 OLE 图片流。

### 第三步：生成前端数据

新增一个转换脚本，将 `data/staging/official-artworks.json` 转成 Desktop 可用结构：

- 221 条正式作品都可以进入正常列表；
- 分类页改为正式分类；
- 搜索字段包括标题、简介、分类、来源文档。

### 第四步：重新生成音频

正式数据确认后再批量生成音频。不要在 staging 未确认时提前生成 221 条，避免重复消耗和后续重命名。
