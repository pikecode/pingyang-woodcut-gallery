> 文档状态：Review Draft

## 1. 执行摘要

项目初始状态只有一份简单的 `README.md` 和一份 441 MB 的旧版 Word 文档
`docs/平阳木版年画.doc`。该文档实际是一份图文藏品目录，而不是项目需求说明。

当前已经完成以下基础工作：

- 从旧版 Word 中恢复 55 条藏品记录、37 个别名和 65 个图片对象。
- 原样提取 65 张图片，没有缩放或重新编码。
- 建立可追溯的 SQLite 数据库、原始 JSON、前端 JSON 和图片迁移清单。
- 将源数据中的冲突、疑似错字和缺失信息记录为 26 条待校问题。
- 建立 React + Vite 前端，实现首页、分类页、搜索筛选和藏品详情弹层。
- 为浏览器生成 65 张 WebP 副本，不修改原始图片。
- 完成生产构建以及桌面端、移动端 Chrome 自动化验证。

当前成果可以作为“可演示、可继续编辑的数据型原型”，但在正式公开发布前，仍需完成
馆藏内容校对、版权确认、尺寸单位确认和图片外部存储接入。

| 问题类型 | 数量 | 说明 |

| 年代字段混入技法 | 5 | 25–29 号将“版印手绘”写入年代 |

| 人物名一致性 | 1 | 2 号“冯彦/冯义”需核对 |
| 史料引用待核 | 1 | 98 号“应勋《风俗演义》”疑有误 |

| 尺寸单位缺失 | 1 | 所有规格均没有明确单位 |

当前策略是不静默修正文案：

- 原文完整保存在 `data/raw/artworks.json` 和数据库原始字段中。
- 可确定的结构问题会标准化，例如将“版印手绘”拆到技法字段。
- 不确定的内容进入 `data_issues`，等待人工校对。
- 尺寸暂按厘米表达，但 `dimension_unit_verified = 0`，表示尚未确认。

## 4. 产品目标与设计原则

### 4.1 当前产品目标

建立一个以真实馆藏为核心的数字画廊，使用户可以：

1. 在首页快速理解平阳木版年画的内容范围和视觉特征。
2. 按题材和形制浏览藏品。
3. 搜索题名、别名和画面说明。
4. 查看作品原图、年代、规格、馆藏和完整简介。
5. 在不重做数据层的前提下，后续接入对象存储和管理后台。

### 4.2 核心原则

- **原始可追溯**：源文档字段、规范字段和待校问题分开存储。
- **图片不进数据库**：数据库只保存路径、格式、尺寸和哈希。
- **原图不重编码**：原图只提取，浏览器版本另行生成。
- **静态优先**：当前数据量小，优先提供低运维成本的静态前端。
- **可迁移**：数据模型不绑定本地文件系统，可切换对象存储或 PostgreSQL。
- **馆藏优先**：界面以扫描、比较、筛选和查看作品为主，不做营销型落地页。

## 6. 数据模型设计

完整结构见 [`data/schema.sql`](../data/schema.sql)。

### 6.1 核心表

| 表 | 职责 |
|---|---|
| `source_documents` | 源文件路径、哈希、大小、格式和导入时间 |
| `artworks` | 藏品规范数据及原始字段副本 |
| `artwork_aliases` | 作品别名、异名 |
| `artwork_images` | 一对多图片、格式、尺寸、哈希和存储信息 |
| `collections` | 馆藏机构 |
| `themes` | 戏曲、神祇、吉祥、故事 |
| `forms` | 门神、门画、灯画 |
| `materials` | 拂尘纸等材质 |
| `techniques` | 版印手绘等技法 |
| `artwork_references` | 预留史料、书目和外部引用 |
| `data_issues` | 冲突、缺失、疑似错字和处理状态 |
| `artworks_fts` | 中文三元全文索引 |

### 6.2 关键建模决定

- `id` 是系统内部主键，`catalog_no` 保留源文档编号，不因缺号而重排。
- `slug` 使用稳定 ASCII 值，例如 `py-001`，便于目录和 URL 使用。
- 年代保存 `period_code`、展示值和原始值，不把“清”“清代”视为不同年代。
- 双联作品使用多条 `artwork_images`，角色暂记为 `part-1/part-2`，没有擅自判断左右。
- 图片表预留 `storage_provider`、`storage_path`、`public_url`，支持后续对象存储。
- 每张原图保存 SHA-256，迁移后可验证文件是否完整。
- 全文索引使用 FTS5 `trigram`，支持中文连续文本搜索。

## 7. 图片资产策略

### 7.1 原图

从 Word `Data` 流识别出 65 个连续图片块，与正文 65 个图片锚点一一对应。

| 格式 | 数量 | 总字节数 |
|---|---:|---:|
| JPEG | 49 | 265,761,692 |
| MPO | 7 | 21,736,301 |
| PNG | 3 | 1,703,869 |
| TIFF | 6 | 169,680,280 |
| 合计 | 65 | 458,882,142 |

原图位于 `assets/originals/{slug}/`，总大小约 438 MB，已经由 `.gitignore` 排除。
原图提取过程没有进行色彩转换、缩放或重新编码。

### 7.2 Web 图片

浏览器对 TIFF 和 MPO 支持不稳定，因此由 `scripts/build_web_assets.py` 生成 WebP 副本：

- 共 65 张。
- 最长边限制为 1800 像素。
- 当前总大小约 20 MB。
- 输出到 `public/images/{slug}/`。
- 前端数据输出到 `public/data/artworks.json`。

### 7.3 外部存储迁移

`data/exports/image-manifest.json` 保存每张原图的作品编号、角色、路径、字节数、尺寸、
格式和 SHA-256。迁移对象存储后，应：

1. 上传原图或 Web 图。
2. 用清单 SHA-256 验证原图。
3. 更新 `artwork_images.storage_provider` 和 `public_url`。
4. 让前端导出流程使用外部 URL。

## 8. 前端规划与当前实现

主要代码：

- [`src/App.jsx`](../src/App.jsx)
- [`src/styles.css`](../src/styles.css)
- [`src/main.jsx`](../src/main.jsx)

### 8.1 首页

首页不采用传统营销站结构，而是让真实年画成为第一视觉信号：

- 全幅馆藏图片首屏。
- 项目名称、简短文化背景和馆藏入口。
- 戏曲、神祇、吉祥、故事四类快捷入口及数量。
- 六件精选藏品。
- 四类题材脉络和代表作品。
- 55 件藏品、65 幅图像等馆藏概览。

### 8.2 分类页

分类页围绕重复浏览和比较设计：

- 主题标签及实时数量。
- 题名、别名、简介搜索。
- 形制筛选。
- 编号或题名排序。
- 网格/列表切换。
- 结果数量和筛选重置。
- 空结果状态。

### 8.3 藏品详情

当前使用详情弹层而不是独立路由：

- 展示一张或两张图片。
- 展示题名、别名、主题、形制、年代、规格、馆藏和完整说明。
- 支持上一件、下一件和关闭。
- 支持键盘 Escape、左右方向键。
- 桌面端采用图像/说明双栏，移动端采用纵向可滚动布局。

### 8.4 视觉方向

- 主色以纸白和墨黑为基础，使用朱红、墨绿和金色作为功能强调。
- 标题采用宋体语气，操作界面使用黑体，提高馆藏感和可读性。
- 不使用渐变、装饰性圆球、嵌套卡片和大面积圆角。
- 图片区域使用稳定宽高比，避免加载时布局跳动。
- 组件圆角控制在 2px，整体更接近图录和展陈系统。

## 11. 当前限制与风险

### 11.1 内容风险

- 40–86 号作品是否真正缺失尚未确认。
- 102 号作品年代存在直接冲突。
- 尺寸单位尚未由馆方确认。
- 26 条数据问题仍为开放状态。
- 当前图片替代文本主要使用题名，尚未建立专门的无障碍图像描述。

### 11.2 版权风险

- 图片版权、数字传播授权和说明文字授权均未确认。
- 页面目前明确保留“版权状态待馆方确认”的提示。
- 正式公开前需要确定版权声明、使用范围和下载策略。

### 11.3 技术风险

- 当前为前端静态数据，没有登录、编辑、审核和发布后台。
- 当前搜索在浏览器中进行，55 条数据没有性能问题，但大规模扩展后需要服务端搜索。
- 使用 `BrowserRouter`，生产托管需要将未知路径回退到 `index.html`。
- 原图仍存放在本地工作区，尚未迁移到对象存储。
- 数据库是导入产物；若未来直接编辑数据库，需要明确如何避免重新导入时覆盖人工修改。
- WebP 当前作为仓库静态资产，是否进入 Git 需要在部署方案确定后决定。

## 15. 当前结论

当前项目已经从一个不可直接消费的 441 MB 图文 Word 文件，转化为一套具有来源追踪、
数据质量记录、图片迁移能力和响应式前端的数字馆藏原型。

技术结构已经能够支撑当前 55 件藏品的展示，并为后续对象存储、独立详情页和管理后台
保留了扩展空间。下一阶段的主要瓶颈不是前端功能，而是馆藏数据校对、版权确认和内容
治理规则。上述三项确认后，再进入正式发布和后台建设更稳妥。
